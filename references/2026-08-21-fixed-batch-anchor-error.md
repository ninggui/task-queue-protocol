# 08-21 修正实录：请求到达非高峰窗口却锚定固定批次（用户纠正）

## 场景

2026-08-21 01:29 用户请求「jspace+dshrouter 插件学习对比」。
当时回复："已入待办队列（P1），今晚 03:00 自主学习优先执行"。

用户 02:12 纠正："你得出 3 点钟之后再运行，这个理论我是不认可的，
因为当前时间段就已经是在现实可以直接执行，你留意一下时间，为什么会出现这样的错误？"

## 根因（两层错误叠加）

1. **没执行"判断先行"**：协议第一条要求先 `date` 看当前时间。
   01:29 已在非高峰窗口（18-次日9）内 → 本应立即执行。
   却机械套用"非紧急→入队→等下批 cron"，把协议从"高峰防打扰机制"误用成"统一延迟器"。

2. **错误锚定固定批次**：任务被指定为「时新插件扫描」机制首个案例，
   就把它绑到夜间自主学习 03:00 cron，以为必须挂那个批次才算"机制案例"。
   实际上机制只规定学习方向，不规定必须 03:00 跑。

## 时间线

- 01:29 收到请求 → 非高峰窗口内 → 可直接执行（实际被排到 03:00，白等 1.5h）
- 01:56 用户说"现在立刻" → 其实没必要，本来就是可执行时段
- 02:12 用户指出错误

## 修正后规则（已写入 SKILL.md 核心规则）

- 非高峰（12-14 / 18-次日9）到达 → **立即执行**，不等任何固定批次
- 入队仅限高峰（9-12 / 14-18）到达
- 批量 cron（12:10/18:10）和夜间自主学习（03:00）只是高峰入队任务的兜底，
  不是非高峰到达请求的延迟器

## 可复用判断

收到请求时第一动作永远是：先看当前时间 → 在非高峰窗口内就做，
只有高峰才考虑入队。不要被"机制首个案例""学习方向"这类标签带偏到固定 cron 时间。
